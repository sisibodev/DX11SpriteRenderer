# DX11 2D 스프라이트 렌더러 — 아키텍처 문서

> Direct3D 11로 직접 구현한 2D 스프라이트 렌더러의 설계와 최적화 기록입니다.
> 개념 단위의 학습 내용은 [LEARNING-NOTES.md](LEARNING-NOTES.md)에 따로 정리했습니다.

---

## 1. 개요

### 1.1 목적

DirectX 11을 직접 사용해 2D 스프라이트 렌더러를 구현한 프로젝트다.
핵심 목표는 **스프라이트 배칭을 통한 드로우콜 최소화**이며, 이를 통해 렌더링 파이프라인과
성능 최적화의 원리를 코드 수준에서 다룬다.

- **개발 기간**: 2026-08-10 ~ 2026-08-23 (14일)
- **개발 인원**: 1인
- **개발 동기**: 13년간 상용 엔진(게임브리오, Unity) 위에서 클라이언트를 개발해왔으나
  그 아래의 렌더링 파이프라인을 직접 다뤄본 경험은 없었다. 그 공백을 메우기 위해
  엔진에 의존하지 않고 렌더러를 처음부터 구현했다.

### 1.2 기술 스택

| 항목 | 내용 |
|---|---|
| 언어 | C++17 |
| 그래픽 API | Direct3D 11 (Feature Level 11.0) |
| 개발 환경 | Visual Studio 2022, Windows 11 (x64) |
| 외부 의존성 | `stb_image` (단일 헤더, 퍼블릭 도메인) |
| 에셋 | Kenney.nl (CC0) |

외부 라이브러리는 **의도적으로 최소화**했다. 특히 `DirectXTK`는 `SpriteBatch`를 이미 제공하므로,
배칭을 직접 구현한다는 프로젝트 목적과 맞지 않아 사용하지 않았다.

### 1.3 실행 방법

```
1. Visual Studio 2022로 DX11SpriteRenderer.sln 열기
2. 구성: Debug 또는 Release / 플랫폼: x64
3. F5 실행
```

셰이더와 에셋은 빌드 후 이벤트로 출력 폴더에 복사되며, 실행 파일 단독으로도 동작한다.

#### 조작

실행 중에 각 최적화를 켜고 끄며 효과를 직접 비교할 수 있다. 현재 상태와 통계는 **창 제목
표시줄**에 실시간으로 표시된다.

| 키 | 기능 |
|---|---|
| `F1` | 배칭 on/off |
| `F2` | 텍스처 정렬 on/off |
| `F3` | 화면 밖 컬링 on/off |
| `F4` | VSync on/off |
| `1` `2` `3` `4` | 엔티티 수 — 1,000 / 5,000 / 10,000 / 50,000 |
| 방향키 | 카메라 이동 |

제목 표시줄 형식:

```
스프라이트 : 13033 | 드로우콜 : 4(1, 2, 1) | 1.02 ms (981 fps)
| 엔티티 50000 | 배칭 ON | 정렬 ON | 컬링 ON | VSync OFF
```

드로우콜 옆 괄호는 **플러시가 일어난 원인별 횟수**(텍스처 전환, 버퍼 포화, 배치 마감)다.
4장의 측정은 전부 이 화면에서 읽은 값이다.

## 2. 아키텍처

### 2.1 전체 구조

```
src/
├─ main.cpp              진입점 (13줄)
├─ core/
│  ├─ App               생명주기 관리 (Initialize / Run / Update / Render)
│  └─ Window            Win32 창 생성, 메시지 루프
├─ render/
│  ├─ GraphicsDevice    D3D11 디바이스·스왑체인·렌더 상태
│  ├─ Shader            HLSL 런타임 컴파일, 파이프라인 바인딩
│  ├─ Texture           이미지 로드 → GPU 텍스처
│  └─ Vertex.h          정점 구조체 + 입력 레이아웃 정의
├─ shaders/             HLSL 소스 (런타임 컴파일)
└─ third_party/         stb_image
```

### 2.2 계층 규칙

의존 방향을 **한쪽으로만** 흐르게 제한했다.

```
main → App → { Window, GraphicsDevice, Shader, Texture }
```

- `render/` 계층은 `core/`를 알지 못한다 (하위가 상위를 참조하지 않음)
- `App`은 조립과 흐름 제어만 담당하고, 실제 작업은 각 클래스에 위임한다
- COM 객체의 수명은 전부 `ComPtr`(RAII)로 관리한다

`App`의 멤버 선언 순서는 소멸 순서를 결정한다. 멤버는 선언의 **역순**으로 소멸하므로,
`Window`를 가장 먼저 선언해 D3D 리소스들이 모두 정리된 뒤에 창이 닫히도록 했다.

### 2.3 렌더링 파이프라인 흐름

```
[정점 버퍼] ─→ IA (Input Assembler)
                 │  InputLayout이 바이트 배열을 정점 구조로 해석
                 ↓
              VS (Vertex Shader)     정점 위치 계산 → SV_POSITION
                 ↓
              RS (Rasterizer)        삼각형 → 픽셀, 정점 값 보간
                 ↓
              PS (Pixel Shader)      텍스처 샘플링 → 최종 색
                 ↓
              OM (Output Merger)     블렌딩 후 렌더타겟에 기록
```

정점에 넣은 색이 삼각형 내부에서 그라데이션으로 나타나는 것은 **RS 단계의 보간** 때문이다.
같은 원리로 UV도 보간되어, 사각형 전체에 텍스처가 늘어나 붙는다.

## 3. 핵심 구현

### 3.1 GraphicsDevice — D3D11 초기화

#### 세 객체의 역할 분리

| 객체 | 역할 |
|---|---|
| `ID3D11Device` | 리소스 **생성** (버퍼, 텍스처, 셰이더, 상태 객체) |
| `ID3D11DeviceContext` | 렌더 **명령 발행** (바인딩, 드로우, 클리어) |
| `IDXGISwapChain` | 화면 버퍼 관리 및 `Present` |

이렇게 나뉜 이유는 **멀티스레딩** 때문이다.

`Device`가 하는 일은 새 객체를 만들어 돌려주는 것뿐이라 **호출 사이에 이어지는 상태가 없다.**
그래서 여러 스레드에서 동시에 호출해도 된다.

반면 `DeviceContext`는 이름 그대로 **"지금 파이프라인이 어떤 상태인가"를 누적해 들고 있다.**
어떤 정점 버퍼가 꽂혀 있고 몇 번 슬롯에 어떤 텍스처가 바인딩됐는지가 여기에 저장된다.
바인딩과 드로우가 여러 호출에 걸쳐 이어지므로, 두 스레드가 동시에 만지면 서로의 설정을 덮어쓴다.

```
스레드 A: 텍스처1 바인드
스레드 B: 텍스처2 바인드      ← A가 꽂은 것을 덮어씀
스레드 A: DrawIndexed          ← 텍스처2로 그려진다
```

에러도 크래시도 없이 **잘못된 그림이 나온다.** 그래서 명령 발행은 한 스레드에서만 해야 한다.

병렬화가 필요하면 스레드마다 **Deferred Context**를 하나씩 두고 명령을 기록한 뒤, 마지막에 한
스레드가 모아서 실행한다. `DeviceContext`에 락을 거는 대신 이런 구조를 택한 이유는, 락을 걸면
결국 한 번에 하나씩 실행되어 병렬화한 의미가 사라지기 때문이다.

이 프로젝트는 단일 스레드로 동작하므로 해당 사항은 없다.

#### 초기화 순서

```
1. DXGI_SWAP_CHAIN_DESC 구성
2. D3D11CreateDeviceAndSwapChain  → Device + Context + SwapChain
3. SwapChain::GetBuffer           → 백버퍼(ID3D11Texture2D) 획득
4. CreateRenderTargetView         → 백버퍼를 '그릴 대상'으로 지정
5. RSSetViewports                 → NDC를 픽셀 좌표로 매핑할 영역
6. CreateSamplerState             → 텍스처 읽기 방식
7. CreateBlendState               → 알파 합성 방식
```

3~4단계가 나뉘어 있는 이유는, 백버퍼 자체는 단순한 텍스처이고 **"이 텍스처를 렌더타겟으로
쓰겠다"는 용도 선언이 View**이기 때문이다. 같은 텍스처라도 용도(렌더타겟 / 셰이더 입력)에 따라
다른 View를 만들어 붙인다.

#### 스왑 효과 — FLIP 모델에서 DISCARD로

처음에는 `DXGI_SWAP_EFFECT_FLIP_DISCARD`(플립 모델)로 스왑체인을 구성했으나
`DXGI_ERROR_INVALID_CALL`로 생성에 실패했다.

원인을 추적한 결과, `D3D11CreateDeviceAndSwapChain`이 내부적으로 **구형 DXGI 1.0 경로**를
사용하기 때문이었다. 플립 모델을 쓰려면 디바이스를 먼저 생성한 뒤
`IDXGIFactory2::CreateSwapChainForHwnd`로 스왑체인을 따로 만들어야 한다.

당시 필요한 것은 화면 출력이 되는 상태였으므로 `DISCARD`(비트블릿 모델)로 전환해 진행했고,
플립 모델 적용은 개선 항목으로 남겼다(5장 참고). 두 모델의 차이는 전체화면 전환의 매끄러움과
화면 합성 단계의 복사 횟수이며, 이 프로젝트 규모에서는 체감되는 차이가 없었다.

#### 렌더 상태의 소유권

상태 객체의 소유권은 **그 상태가 바뀌는 주기**에 따라 나눴다.

| 상태 | 소유자 | 바인딩 시점 | 이유 |
|---|---|---|---|
| `SamplerState` | `GraphicsDevice` | `BeginFrame` | 전체에 걸쳐 동일 |
| `RasterizerState` | `GraphicsDevice` | `BeginFrame` | `CULL_NONE` 고정 (3.4 참고) |
| `BlendState` | **`SpriteBatch`** | `Begin` | **배치마다 달라질 수 있음** |

처음에는 블렌드 상태도 `GraphicsDevice`가 갖고 있었다. 가산 블렌딩(이펙트용)을 추가하면서
**블렌드는 프레임의 성질이 아니라 배치의 성질**이라는 것이 분명해져 `SpriteBatch`로 옮겼다.

`GraphicsDevice`에는 **프레임 단위로 변하지 않는 것만** 남는다 — 디바이스, 스왑체인,
렌더타겟 뷰, 샘플러, 래스터라이저. 알파와 가산을 오가야 하는 블렌드는 배치를 소유한 쪽에
있어야 `Begin`의 인자로 자연스럽게 노출된다.

### 3.2 Shader — 런타임 컴파일

셰이더를 빌드 시점이 아닌 **런타임에 컴파일**한다(`D3DCompileFromFile`).
셰이더만 수정하고 다시 실행하면 되므로 반복 속도가 빠르고, 컴파일 오류를 실행 중에
확인할 수 있다.

가장 중요한 부분은 **에러 블롭 출력**이다.

```cpp
if (FAILED(hr))
{
    if (errorBlob)
        printf("[셰이더 컴파일 실패]\n%s\n",
               static_cast<const char*>(errorBlob->GetBufferPointer()));
}
```

이 출력이 없으면 "컴파일에 실패했다"는 사실만 알 뿐 원인을 알 수 없다.
`ID3DBlob`은 크기 정보를 가진 이진 데이터 덩어리로, 여기서는 에러 메시지를,
성공 시에는 컴파일된 셰이더 바이트코드를 담는다.

#### InputLayout이 셰이더 바이트코드를 요구하는 이유

```cpp
device->CreateInputLayout(layout, layoutCount,
                          vsBlob->GetBufferPointer(), vsBlob->GetBufferSize(),
                          &m_inputLayout);
```

D3D가 **선언한 정점 구조와 셰이더의 실제 입력 시그니처가 일치하는지 생성 시점에 검증**하기
위해서다. 시맨틱 이름이나 개수가 맞지 않으면 여기서 실패하므로, 런타임에 화면이 깨지는 대신
초기화 단계에서 문제를 잡을 수 있다.

### 3.3 Texture — 이미지 로드

```
stb_image로 디코드 (RGBA 4채널 강제)
  → CreateTexture2D (D3D11_USAGE_IMMUTABLE)
  → stbi_image_free (CPU 메모리 해제)
  → CreateShaderResourceView
```

- **4채널 강제**: D3D에는 24비트 RGB 포맷이 없어 항상 RGBA로 변환한다
- **`SysMemPitch`**: 이미지 한 줄의 바이트 수(`너비 × 4`). 이 값이 틀리면 이미지가
  대각선으로 밀려 나타난다
- **`USAGE_IMMUTABLE`**: 업로드 후 변경하지 않으므로 GPU가 가장 효율적으로 배치할 수 있다
- `ID3D11Texture2D` 핸들은 보관하지 않는다. `ShaderResourceView`가 참조를 유지하고,
  셰이더에서 쓰려면 어차피 View가 필요하기 때문이다

#### 텍스처와 샘플러를 분리하는 이유

텍스처는 *무엇을 읽는가*, 샘플러는 *어떻게 읽는가*를 담당한다.
같은 텍스처를 선명하게도 부드럽게도 읽을 수 있어야 하고, 반대로 여러 텍스처가 같은 읽기
방식을 공유하는 경우가 대부분이다. 그래서 샘플러는 몇 개만 만들어 재사용한다.

이 프로젝트는 `D3D11_FILTER_MIN_MAG_MIP_POINT`를 선택했다. 사용한 에셋이 16×16 픽셀 아트라
`LINEAR`로 보간하면 확대할 때 경계가 뭉개진다. `POINT`는 가장 가까운 텍셀을 그대로 가져오므로
원본의 픽셀 경계가 유지된다.

이 선택은 나중에 아틀라스를 도입할 때 부수적인 이득도 있었다. 타일 경계에서 인접 타일의 픽셀이
새어 나오는 현상(bleeding)은 보간 때문에 생기는데, `POINT`에서는 **정수 배율로 그리는 한**
발생하지 않는다. 실제로 16px 타일을 32px(정확히 2배)로 그린 결과 경계가 깨끗했다.

### 3.4 SpriteBatch — 배칭

이 프로젝트의 핵심이다.

#### 문제

스프라이트를 하나 그릴 때마다 정점 버퍼를 갱신하고 `DrawIndexed`를 호출하면, 드로우콜이
스프라이트 수만큼 발생한다. 드로우콜은 CPU가 GPU에 작업을 제출하는 단위이고 매번 드라이버
검증과 상태 확인이 따라붙으므로, 개수가 늘면 CPU가 병목이 된다.

#### 구조

```
Begin(camera, blendMode)
  ├ 카메라 행렬 업로드 (프레임당 1회)
  ├ 정점·인덱스 버퍼, 셰이더, 블렌드 상태 바인딩
  └ 누적 버퍼 비우기

Draw(texture, desc)  × N
  ├ 플러시 조건 검사
  └ 정점 4개를 CPU 벡터에 누적          ← GPU 호출 없음

End()
  └ Flush — 누적분을 한 번에 업로드하고 DrawIndexed 1회
```

`Draw`는 **GPU를 전혀 건드리지 않는다.** CPU 메모리에 정점을 쌓기만 하고, 실제 제출은
`Flush`에서 한 번에 일어난다.

#### 정점 버퍼는 동적, 인덱스 버퍼는 정적

| | Usage | 갱신 시점 |
|---|---|---|
| 정점 버퍼 | `DYNAMIC` + `MAP_WRITE_DISCARD` | 플러시마다 |
| 인덱스 버퍼 | `DEFAULT` | 초기화 때 1회 |

정점은 매 프레임 바뀌지만 인덱스 패턴 `0,1,2 / 0,2,3`은 **영원히 고정**이다. 최대 개수만큼
미리 만들어두고 다시 건드리지 않는다.

`MAP_WRITE_DISCARD`는 "이전 내용을 버리겠다"는 선언이다. 드라이버가 GPU가 사용 중인 버퍼를
기다리는 대신 새 메모리 영역을 내주므로, CPU가 GPU를 기다리며 멈추지 않는다.

#### 플러시가 일어나는 두 지점

```cpp
if (m_currentTexture != nullptr && m_currentTexture != &texture)
    Flush(FlushReason::TextureChange);

if (m_cpuVertices.size() + 4 > m_maxVertexCount)
    Flush(FlushReason::BufferFull);
```

**두 이유를 구분해 세는 것이 중요하다.** "드로우콜이 300개"라는 사실만으로는 무엇을 고쳐야
할지 알 수 없기 때문이다.

| 원인 | 처방 |
|---|---|
| 텍스처 전환 | 텍스처 기준 정렬, 아틀라스 통합 |
| 버퍼 포화 | `maxSpriteCount` 증설 |

집계는 **early-return 가드를 통과한 뒤**에 수행한다. 호출부에서 세면, 버퍼 포화로 방금 비운
직후 텍스처가 바뀌는 경계에서 정점이 0개인 채로 텍스처 분기가 걸려 **실제 드로우콜 없이
카운터만 오른다.**

검산식 `drawCall == textureSwitch + overflow + endOfBatch` 가 항상 성립해야 한다.
4장의 모든 측정에서 이 식이 성립했고, 배칭 미적용 조건에서는 `= 스프라이트 수`까지 일치했다.

#### 설계 원칙 — 상태는 고정, 변화는 정점 데이터로

배칭이 유지되려면 배치 도중에 파이프라인 상태가 바뀌면 안 된다. 그래서 스프라이트마다
달라지는 값은 **전부 정점 데이터 쪽으로 밀어 넣었다.**

| 스프라이트마다 다른 것 | 이 프로젝트의 처리 | 상태로 처리했다면 |
|---|---|---|
| 위치·회전·크기 | CPU에서 정점 좌표 계산 | 상수 버퍼 변경 → 끊김 |
| 색상(틴트) | 정점 색상 | 상수 버퍼 변경 → 끊김 |
| 그림 종류 | UV (아틀라스) | 텍스처 변경 → 끊김 |
| 좌우 반전 | 음수 크기 + `CULL_NONE` | 컬 모드 변경 → 끊김 |

회전을 상수 버퍼 대신 CPU에서 계산하는 이유, 틴트를 정점 색상에 넣는 이유, 아틀라스를 쓰는
이유, 컬 모드를 하나로 통일한 이유가 **모두 같은 원칙에서 나온다.**

2D는 모든 쿼드가 카메라를 정면으로 보므로 백페이스 컬링으로 버릴 것이 없다. 뒷면 판정이
나오는 것은 좌우 반전(음수 스케일)으로 와인딩이 뒤집혔을 때뿐이고, 그것은 보고 싶었던
스프라이트다. 반전 여부에 따라 컬 모드를 나누면 `RSSetState`가 상태 변경이 되어 텍스처 교체와
똑같이 배치를 끊으므로, **존재하지 않는 이득을 위해 실제 드로우콜을 늘리는 셈이 된다.**
그래서 `CULL_NONE` 하나로 고정했다.

#### 정점에 넣을 수 없는 것은 API가 제약을 드러내게

블렌드 모드는 파이프라인 상태라 정점에 담을 수 없다. 그래서 **배치 단위로만 지정**하도록
`Begin`의 인자로 받는다.

```cpp
void Begin(const Camera2D& camera, BlendMode mode = BlendMode::Alpha);
```

시그니처만 봐도 "배치 중간에는 바꿀 수 없다"가 읽힌다. XNA `SpriteBatch.Begin(sortMode,
blendState)` 도 같은 형태다.

알파와 가산 두 상태는 **초기화 때 미리 만들어 교체**한다. D3D11의 상태 객체는 불변이라
`GetDesc`로 꺼내 수정해도 반영되지 않기 때문이다. 드라이버가 생성 시점에 설정을 검증하고
하드웨어 레지스터 값으로 번역해두는 구조이므로, 나중에 바꿀 수 있게 하면 그 설계가 의미를
잃는다. D3D9의 `SetRenderState`가 D3D10에서 상태 객체 모델로 바뀐 이유이기도 하다.

## 4. 최적화

### 4.1 측정 환경과 방법

| 항목 | 값 |
|---|---|
| GPU | NVIDIA GeForce RTX 3080 |
| 해상도 | 1280 × 720 (창 모드) |
| 빌드 | **Release / x64** |
| VSync | **해제** (`Present(0, 0)`) |
| 측정값 | 0.5초 누적 평균 프레임 타임 |

**Release 빌드로 측정해야 한다.** Debug는 STL 반복자 검사 때문에 `std::sort`와 벡터 접근이
몇 배 느려 수치가 의미를 잃는다.

측정 정확도를 위해 두 가지를 별도로 처리했다.

- **디버그 레이어를 `_DEBUG`에서만 활성화** — 드로우콜마다 인자를 검증하므로, 켜두면 배칭
  없는 경로가 실제보다 훨씬 느리게 측정된다
- **클램프 전 원본 델타타임으로 집계** — 델타타임 상한(0.1초)은 창 이동 등으로 루프가 멈췄을
  때 게임 로직을 보호하기 위한 것인데, 그대로 측정에 쓰면 100ms를 넘는 프레임이 전부 100ms로
  기록되어 **가장 느린 구간이 통째로 사라진다**

씬은 **고정 시드**로 생성한다. 실행마다 배치가 달라지면 "최적화 덕분인지 배치가 유리했던
것인지" 구분할 수 없기 때문이다.

#### 조건

기능을 하나씩 켜 나가며 각 단계의 기여를 분리했다.

| 조건 | 배칭 | 텍스처 정렬 | 화면 밖 컬링 |
|---|---|---|---|
| **A** | — | — | — |
| **B** | ✓ | — | — |
| **C** | ✓ | ✓ | — |
| **D** | ✓ | ✓ | ✓ |

A는 `maxSpriteCount = 1`인 별도 `SpriteBatch`로 구현했다. **같은 코드 경로에 버퍼 크기만
다르므로** "구현이 달라서 느린 것 아니냐"는 반론의 여지가 없다.

월드는 뷰포트의 4배 넓이이고 엔티티가 그 안에 균등히 분포하므로 약 75%가 화면 밖에 있다.
텍스처는 두 종류를 무작위로 배정해 **정렬 이전의 최악 상태**를 만들었다.

### 4.2 결과

**프레임 타임 (ms)**

| 엔티티 | A | B | C | D | **A → D** |
|---|---|---|---|---|---|
| 1,000 | 0.46 | 0.46 | 0.13 | **0.12** | 3.8배 |
| 5,000 | 2.38 | 1.97 | 0.26 | **0.14** | 17.0배 |
| 10,000 | 4.55 | 3.89 | 0.49 | **0.21** | 21.7배 |
| 50,000 | **28.19** | 19.01 | 2.22 | **1.02** | **27.6배** |

측정 편차는 같은 조건을 반복했을 때 **약 3%** 였다(50,000 C 조건에서 2.22 / 2.28ms).
이보다 작은 차이는 유의미하지 않은 것으로 본다.

**드로우콜** — 괄호는 (텍스처 전환, 버퍼 포화, 배치 마감)

| 엔티티 | A | B | C | D |
|---|---|---|---|---|
| 1,000 | 1000 (522, 477, 1) | 523 (522, 0, 1) | 2 (1, 0, 1) | 2 (1, 0, 1) |
| 5,000 | 5000 (2560, 2439, 1) | 2561 (2560, 0, 1) | 2 (1, 0, 1) | 2 (1, 0, 1) |
| 10,000 | 10000 (5110, 4889, 1) | 5111 (5110, 0, 1) | 4 (1, 2, 1) | 2 (1, 0, 1) |
| 50,000 | 50000 (25165, 24834, 1) | 25166 (25165, 0, 1) | 14 (1, 12, 1) | 4 (1, 2, 1) |

모든 A 조건에서 `전환 + 포화 + 마감 = 스프라이트 수`가 정확히 성립한다. 배칭 미적용 경로가
의도대로 "스프라이트당 드로우콜 1개"로 동작함이 수치로 확인된다.

### 4.3 발견

#### ① 최적화 효과는 규모에 비례해 커진다

```
1,000개 → 3.8배      5,000개 → 17.0배
10,000개 → 21.7배    50,000개 → 27.6배
```

1,000개 규모에서는 A와 B의 차이가 아예 없다(0.46 = 0.46). **적은 수에서는 최적화가 무의미하고
규모가 커질 때 비로소 필요해진다**는 것이 수치로 드러난다.

#### ② 비싼 것은 드로우콜 개수가 아니라 상태 변경이다

50,000개 기준으로 두 구간을 비교하면 —

```
A → B   드로우콜 50000 → 25166 (절반)     28.19 → 19.01 ms   1.5배
B → C   텍스처 전환 25165 → 1             19.01 →  2.22 ms   8.6배
```

**드로우콜을 절반으로 줄여 1.5배, 텍스처 전환을 25,000분의 1로 줄여 8.6배다.**
네 지점 모두에서 같은 패턴이 재현됐다.

A의 추가 플러시(포화 24,834회)는 대부분 **같은 텍스처를 다시 바인딩**하는 것이라 실질적인
상태 변경이 발생하지 않는다. 그래서 드로우콜 개수 차이에 비해 시간 차이가 작다.

따라서 정확한 표현은 "드로우콜을 줄여라"가 아니라 **"상태 변경을 줄여라"** 다.

#### ③ 60fps 경계

50,000개, 16.67ms 기준:

| 조건 | 프레임 타임 | 60fps |
|---|---|---|
| A | 28.19 ms (35 fps) | ✗ |
| B | 19.01 ms (53 fps) | ✗ |
| C | 2.22 ms (450 fps) | ✓ |
| D | 1.02 ms (981 fps) | ✓ |

**배칭만으로는 부족하다.** 텍스처가 뒤섞여 있으면 배칭을 해도 60fps를 지키지 못한다.

#### ④ 각 최적화는 서로 다른 것을 줄인다

| 최적화 | 줄이는 것 | 관찰되는 지표 |
|---|---|---|
| 배칭 | 드로우콜 제출 횟수 | 드로우콜 |
| 텍스처 정렬 | **상태 변경 횟수** | 드로우콜 |
| 화면 밖 컬링 | **정점 생성 · 픽셀 처리** | 스프라이트 수, 프레임 타임 |

컬링은 드로우콜을 줄이지 않는다. C와 D는 둘 다 드로우콜이 2인데 시간은 절반 아래다
(5,000개 기준 0.26 → 0.14ms). 줄어든 것은 순수하게 **정점 생성과 픽셀 처리**다.

원인별 카운터가 없으면 이 구분이 보이지 않는다. 드로우콜만 보면 컬링은 "효과 없는 최적화"로
오독된다.

### 4.4 채택하지 않은 최적화 — 버퍼 용량 증설

50,000개 C 조건에서 카운터가 `14 (1, 12, 1)` 을 가리켰다. **텍스처 전환은 이미 1인데 버퍼
포화가 12회**로, 배치를 끊는 주범이 바뀐 것이다. `maxSpriteCount`가 4,096인데 정렬된 텍스처
블록이 각각 25,000개씩이라 블록마다 6회씩 넘친 결과다.

처방은 명확해 보였다. 용량을 8배(4,096 → 32,768)로 올려 재측정했다.

| `maxSpriteCount` | 드로우콜 | 프레임 타임 |
|---|---|---|
| 4,096 | 14 (1, 12, 1) | 2.28 ms (438 fps) |
| 32,768 | **2** (1, 0, 1) | **2.33 ms (430 fps)** |

**드로우콜을 14에서 2로 줄였는데 오히려 2% 느리다.** 4.2에서 확인한 측정 편차가 약 3%이므로,
이 차이는 **노이즈 범위 안이다.** 즉 개선도 악화도 아닌 "차이 없음"이 정확한 결론이다.

반면 메모리는 실제로 늘었다.

| | 4,096 | 32,768 |
|---|---|---|
| 정점 버퍼 (GPU) | 576 KB | 4.5 MB |
| 인덱스 버퍼 (GPU) | 96 KB | 768 KB |
| CPU 정점 벡터 | 576 KB | 4.5 MB |
| **합계** | **약 1.2 MB** | **약 9.8 MB** |

**메모리 8배를 쓰고 성능은 그대로이므로 채택하지 않고 4,096으로 되돌렸다.**

이 결과는 발견 ②를 독립적으로 재확인해준다. 앞에서는 "드로우콜 절반에 1.4배"였는데 여기서는
"드로우콜 7분의 1에 변화 없음"이다. **절대 개수가 이미 작으면 더 줄여도 아무 일도 일어나지
않는다.**

병목이 버퍼 용량으로 이동한 것은 맞지만 **이동한 곳이 이미 저렴했다.** 5만 개 규모에서 실제로
남아 있던 비용은 정점 생성과 픽셀 처리였고, 그것을 잡은 것은 컬링이다(2.22 → 1.02ms).

### 4.5 한계 — 텍스처 정렬이 그리는 순서를 무너뜨린다

2D는 깊이 버퍼 없이 **나중에 그린 것이 위에 오는** 페인터 방식이다. 텍스처 기준으로 정렬하면
그 순서가 무너진다.

실제로 컬링과 정렬을 함께 켰을 때 **겹친 스프라이트가 깜빡이는 현상**이 나타났다. 원인은 두
최적화의 상호작용이었다.

```
정렬 도입 →  비교 함수가 텍스처만 보므로 같은 텍스처끼리 순서가 미정의
             (std::sort는 불안정 정렬)
컬링 도입 →  화면을 드나드는 엔티티 때문에 정렬 입력 배열이 매 프레임 달라짐
합쳐지면  →  같은 텍스처 스프라이트의 앞뒤가 프레임마다 뒤바뀌어 깜빡임
```

**컬링만 끄면 증상이 사라지는 것**으로 원인을 확인했다. 컬링이 없으면 입력 배열이 항상
`0 … n-1`로 동일해 정렬 결과도 매 프레임 같아지기 때문이다.

#### 1차 처방과 그 대가

비교 함수에 엔티티 인덱스를 2차 기준으로 추가해 전순서를 만들었다.

```cpp
if (ta != tb) return ta < tb;
return a < b;                    // 동점이면 인덱스 순
```

깜빡임은 사라졌다. 그런데 **프레임 타임이 41% 느려졌다.**

| | 50,000 D 조건 | 화면 |
|---|---|---|
| 정렬만 | 1.13 ms (884 fps) | 깜빡임 |
| 정렬 + 타이브레이커 | **1.62 ms (616 fps)** | 정상 |

원인은 **비교 횟수**였다. 13,000개를 정렬하면 비교 함수가 약 18만 회(13,000 × log₂13,000)
호출되는데, 추가된 `if (ta != tb)` 가 예측하기 어려운 분기다. 정렬 초반에는 대부분 참이고
같은 텍스처 그룹 안으로 들어가면 대부분 거짓이라 분기 예측이 계속 빗나간다.

```
180,000회 × 약 15 사이클 ÷ 3GHz ≈ 0.9 ms
```

실측 차이(0.49ms)와 같은 자릿수다. **비교 함수에 한 줄을 넣은 대가가 41%였다.**

#### 2차 처방 — 애초에 정렬이 필요 없었다

텍스처가 2종류뿐이라면 순서를 매길 이유가 없다. **두 번 훑어 나눠 담으면 끝이다.**

```cpp
for (int i = 0; ...) {
    if (컬링 통과 안 함) continue;
    m_buckets[e.textureIndex].push_back(i);      // 비교 0회
}
m_drawOrder = buckets[0] + buckets[1];
```

| | 정렬 | 버킷 분류 |
|---|---|---|
| 복잡도 | O(n log n) | **O(n)** |
| 비교 함수 호출 | 약 180,000회 | **0회** |
| 분기 예측 실패 | 많음 | 없음 |
| 결정성 | 타이브레이커 필요 | **구조적으로 보장** |

인덱스 오름차순으로 훑으며 담으므로 같은 텍스처 안에서 항상 같은 순서가 나온다.
**결정성이 별도 비용 없이 따라온다.**

| 방식 | 50,000 D 조건 | 화면 |
|---|---|---|
| 정렬만 | 1.13 ms (884 fps) | 깜빡임 |
| 정렬 + 타이브레이커 | 1.62 ms (616 fps) | 정상 |
| **버킷 분류** | **1.02 ms (981 fps)** | **정상** |

타이브레이커 대비 **34% 빠르고**, 깜빡이던 버전보다도 빠르다.
**정확성을 위해 성능을 지불할 필요가 없었다.** 문제를 정렬로 규정한 것 자체가 잘못이었다.

> 이 프로젝트에서 가장 값어치 있었던 구간이다. 고쳤더니 느려졌고, 왜 느려졌는지 재서
> 원인을 찾았고, 그 원인을 없애는 다른 방법을 찾았다. 첫 처방에서 멈췄다면 41%를
> 그대로 지불한 채 "해결했다"고 적었을 것이다.

#### 남은 한계

**버킷 분류는 결정적 순서를 보장할 뿐 올바른 깊이 순서는 아니다.** 같은 텍스처 스프라이트는
여전히 화면상 위치와 무관한 인덱스 순으로 그려진다. 실제 게임이라면 레이어를 먼저 나누고 그
안에서만 텍스처별로 묶거나(Unity의 Sorting Layer), 불투명은 텍스처 기준 · 반투명은 깊이
기준으로 분리해야 한다.

**이 프로젝트의 텍스처 그룹화는 반투명 스프라이트가 겹치는 씬에서는 그대로 쓸 수 없다.**

또한 버킷 방식은 **텍스처 종류가 적을 때 유효하다.** 종류가 수십·수백으로 늘면 버킷 배열
관리 비용이 커지므로, 그때는 다시 정렬이나 해시 기반 그룹화를 검토해야 한다.

## 5. 회고

### 프로젝트 진행 방식

2주라는 제약 안에서 처음 다루는 스택을 익혀야 했기에, 학습 도구로 AI를 적극 활용했다.
다만 코드 생성에 의존하기보다 **단계별 일정을 먼저 설계하고, 각 단계에서 필요한 개념을
이해한 뒤 직접 구현하는 방식**을 택했다. 발생한 문제는 증상에서 멈추지 않고 원인을 규명해
아래에 정리했다.

결과적으로 이 프로젝트에서 얻은 것은 렌더러 코드 자체보다, **모르는 영역을 짧은 기간에
실무 수준까지 끌어올리는 방법**에 가깝다.

### 겪은 문제와 해결

**① C++와 HLSL의 인코딩 요구가 정반대였다**
MSVC는 BOM이 없으면 파일을 시스템 코드페이지(CP949)로 해석해 한글 주석이 깨진다.
반대로 셰이더 컴파일러(FXC)는 BOM이 있으면 `error X3000: Illegal character`로 실패한다.
`.editorconfig`에서 확장자별로 인코딩을 분리 지정해 해결했다.

**② 0으로 초기화한 구조체의 함정**
`DXGI_SWAP_CHAIN_DESC`에서 `OutputWindow`와 `Windowed`를 채우지 않아
`DXGI_ERROR_INVALID_CALL`이 발생했다. `= {}`로 0 초기화하면 `Windowed = FALSE`가 되는데,
이는 "전체화면"이라는 **유효한 값**이라 컴파일러가 잡아줄 수 없었다.
D3D 설정 구조체는 필드를 하나씩 짚어가며 채웠는지 확인하는 습관이 필요하다고 느꼈다.

**③ 만들었지만 바인딩하지 않은 리소스**
`SamplerState`를 생성해두고 `PSSetSamplers` 호출을 누락했다. 슬롯이 비면 D3D가 기본
샘플러를 사용하므로 **에러도 없고 화면도 정상이지만, 의도한 설정이 무시되는** 상태였다.
동작한다고 해서 의도대로 동작하는 것은 아니라는 걸 확인한 사례다.

**④ 같은 실수가 서로 다른 모습으로**
지역 변수의 주소나 참조를 함수 밖으로 내보내는 실수를 형태만 바꿔 반복했다.

| 형태 | 사라지는 것 | 증상 |
|---|---|---|
| `AnimationClip walk;` 를 만들고 주소를 등록 | 지역 구조체와 내부 `vector`의 힙 버퍼 | 애니메이션이 안 나옴 |
| `Texture tex = m_texture;` 로 복사 후 그리기 | 루프 지역 변수 | 텍스처 전환이 감지되지 않음 |

증상이 서로 달라 처음에는 별개의 문제로 보였지만, 원인은 하나였다 —
**주소를 보관하는 쪽이 대상보다 오래 산다.** 이후로는 참조를 저장하는 코드를 볼 때
"이 대상은 누가 소유하고 얼마나 사는가"를 먼저 확인하게 됐다.

**⑤ 타입 시스템으로 막을 수 있었던 것들**
`SpriteBatch& m_batch = m_spriteBatch;` 로 두고 `m_batch = m_naiveBatch;` 를 실행했다.
참조는 재바인딩되지 않으므로 이는 **복사 대입**이었고, 용량 4,096짜리 배치가 1짜리로
덮어써져 되돌릴 수 없게 됐다. 토글을 다시 눌러도 복구되지 않아 원인 파악이 늦어졌다.

멤버가 전부 복사 가능하면(`ComPtr`, `std::vector`) 컴파일러가 복사 연산을 자동으로
만들어준다. GPU 리소스를 소유한 클래스에서 이는 의도가 아니므로, `Texture` · `Shader` ·
`SpriteBatch`의 복사를 삭제했다. **이 두 줄이 있었다면 위 버그와 ④의 두 번째 사례가
모두 컴파일 에러로 잡혔다.**

값이 싸다면 규칙보다 타입으로 못 박는 편이 확실하다는 것을 확인했다.

**⑥ 구성별로 따로 설정하던 습관이 이 프로젝트에서는 손해였다**
측정을 위해 Release로 처음 빌드하는 시점에 다섯 가지가 동시에 터졌다. **Debug에만 설정하고
Release에는 적용하지 않은 항목들이었다.**

| 누락 항목 | 증상 |
|---|---|
| 추가 포함 디렉터리 | 컴파일 에러 |
| C++ 언어 표준 | 링크 에러 |
| 셰이더 빌드 제외 | 컴파일 에러 |
| assets 복사 (빌드 후 이벤트) | **빌드 성공, 실행만 조용히 종료** |
| 디버거 작업 디렉터리 | **셰이더만 실패, 텍스처는 우연히 성공** |

앞의 셋은 즉시 드러나지만 뒤의 둘은 그렇지 않았다. 특히 작업 디렉터리가 프로젝트 폴더로
잡히는 바람에 텍스처는 **원본 소스 폴더에서 로드되어 성공**하고 셰이더만 실패해, 한동안
셰이더 경로 문제로 오해했다.

원인은 습관이었다. 이전 업무에서는 Debug와 Release의 설정을 **의도적으로 다르게** 가져가는
경우가 많아 구성별로 따로 설정하는 것이 몸에 배어 있었다. 그래서 이번에도 Debug를 먼저
설정하고 Release는 나중에 손보려 했는데, **그 "나중"을 잊은 채로 진행했다.**

뒤늦게 Release 설정을 맞추려니 이번에는 **Debug에서 무엇을 어떻게 설정했는지가 정확히
기억나지 않아** 하나씩 대조해가며 찾아야 했다. 다섯 가지가 한꺼번에 터진 것도 그래서다.

이 프로젝트는 두 구성이 **같은 환경으로 동작하면 되는 경우**였다. 처음부터 속성 창의 구성을
**"모든 구성"으로 두고 한 번에 설정했다면 애초에 생기지 않았을 문제**다.

구성별 분리가 필요한 상황과 그렇지 않은 상황을 먼저 판단하고, 필요 없다면 한 번에 설정하는
편이 낫다는 것을 확인했다. 분리해두면 그 차이는 **다른 구성으로 빌드하는 순간에야 드러나고,
그 순간이 하필 마감 직전인 경우가 많다.**

**⑦ 계측 자체가 틀릴 수 있다**
측정을 시작하기 직전에 계측 코드의 문제 두 가지를 발견했다.

- **델타타임 클램프** — 창 이동 시 순간이동을 막으려고 넣은 0.1초 상한을 그대로 측정에
  썼다. 그대로 뒀다면 50,000개 배칭 미적용 조건(실측 28.19ms)이 아니라 **모든 느린
  조건이 정확히 100.00ms로 기록**됐을 것이다
- **디버그 레이어** — 조건 없이 항상 켜져 있었다. 드로우콜마다 인자를 검증하므로
  **배칭 없는 경로가 실제보다 훨씬 느리게 나와** 배칭 효과를 부풀렸을 것이다

둘 다 "측정 대상"이 아니라 "측정 도구"의 문제였고, 결과만 보고는 알아채기 어려운
종류였다. 수치를 신뢰하기 전에 **그 수치가 어떻게 만들어지는지**를 먼저 확인해야 한다.

### 개선하고 싶은 부분

**렌더링**
- **인스턴싱** — 정점 4개와 인스턴스 버퍼로 전환하면 정점 생성 비용 자체가 사라진다.
  4장에서 확인했듯 상태 변경을 제거한 뒤 남는 비용이 정점 생성과 픽셀 처리이므로,
  다음 단계로 가장 효과가 클 지점이다
- **레이어 기반 정렬** — 4.5의 한계를 해소하려면 레이어를 먼저 나누고 그 안에서만
  텍스처 정렬을 해야 한다. 현재 구현은 반투명 스프라이트가 겹치는 씬에 쓸 수 없다
- 플립 모델 스왑체인(`CreateSwapChainForHwnd`) 적용

**구조**
- `GraphicsDevice.h`가 D3D11 의존성을 외부로 노출한다. 규모가 커지면 PIMPL로 감출 수
  있으나, 현 규모에서는 복잡도 대비 이득이 적다고 판단해 보류했다
- 데모 씬 로직이 `App`에 함께 있다. 엔티티·스폰·갱신·그리기를 `DemoScene`으로 분리하면
  렌더러 라이브러리와 사용 예제의 경계가 분명해진다

**배포**
- 셰이더 사전 컴파일(`.cso`) — 런타임 컴파일은 개발 중 반복 속도에 유리하지만, 배포
  시점에는 시작 시간과 컴파일러 의존성 면에서 사전 컴파일이 낫다
