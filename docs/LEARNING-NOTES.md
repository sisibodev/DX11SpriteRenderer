## Win32 · 윈도우

### Q. `WndProc`의 `wParam` / `lParam`은 무엇인가

메시지 종류에 따라 **의미가 달라지는 범용 데이터 슬롯**이다.
하나의 콜백이 수백 종류의 메시지를 처리해야 하는데 시그니처는 고정이므로,
`msg` 값을 열쇠로 삼아 두 인자를 해석하는 구조다.

| 메시지 | wParam | lParam |
|---|---|---|
| `WM_KEYDOWN` | 가상 키 코드 | 반복 횟수·스캔코드 |
| `WM_SIZE` | 크기변경 종류 | `LOWORD`=너비, `HIWORD`=높이 |
| `WM_MOUSEMOVE` | 보조키 상태 | `LOWORD`=x, `HIWORD`=y |

`w`=WORD, `l`=LONG은 Win16 시절의 흔적이며, 64비트에서는 둘 다 64비트다.
마우스 좌표는 음수가 될 수 있으므로 `LOWORD` 대신 `GET_X_LPARAM`(`windowsx.h`)을 써야 안전하다.

### Q. `PeekMessage`와 `GetMessage`의 차이

- `GetMessage` — 메시지가 없으면 **블로킹**. 입력이 있을 때만 동작하면 되는 일반 앱용
- `PeekMessage` — 없으면 즉시 반환. **매 프레임 렌더링해야 하는 게임 루프용**

게임 루프에 `GetMessage`를 쓰면 입력이 없을 때 화면이 멈춘다.

### Q. C 스타일 콜백에서 C++ 인스턴스에 어떻게 접근하나

`WndProc`은 OS가 호출하는 함수 포인터라 `static`이어야 하는데, 멤버 변수에는 접근해야 한다.

1. `CreateWindowEx`의 마지막 인자로 `this`를 넘긴다
2. `WM_NCCREATE`에서 `CREATESTRUCT::lpCreateParams`로 꺼낸다
3. `SetWindowLongPtr(hWnd, GWLP_USERDATA, this)`로 그 창에 등록한다
4. 이후 메시지에서는 `GetWindowLongPtr`로 꺼내 멤버 함수에 위임한다

전역 변수나 static 인스턴스로 때우는 방식과 달리, **창이 여러 개여도 동작**한다.

### Q. `AdjustWindowRect`는 왜 필요한가

`CreateWindowEx`에 주는 크기는 테두리·타이틀바를 **포함한** 전체 크기다.
그냥 1280을 주면 실제 그림이 그려지는 클라이언트 영역은 그보다 작아지고,
스왑체인 해상도와 어긋나 화면이 늘어나 보인다.

### Q. `QueryPerformanceFrequency`와 `QueryPerformanceCounter`의 차이

자에 비유하면 **주파수는 자의 규격, 카운터는 지금 바늘이 가리키는 눈금**이다.

| | 반환값 | 호출 횟수 |
|---|---|---|
| `QueryPerformanceFrequency` | **초당 틱 수** | 한 번 (부팅 후 불변) |
| `QueryPerformanceCounter` | **현재 누적 틱** | 매 프레임 |

카운터가 주는 틱은 단위 없는 숫자라 그것만으로는 시간을 알 수 없다. 주파수로 나눠야 초가 된다.

```
경과 초 = (지금 카운터 − 이전 카운터) / 주파수
```

API가 초를 바로 주지 않고 둘로 나눠놓은 이유는 두 가지다.

- **주파수는 부팅 후 고정**이라 매 프레임 물어볼 이유가 없다
- **틱은 정수라 오차가 없다.** 저장은 정수(`long long`)로 하고 쓸 때만 환산하면
  부동소수점 오차가 누적되지 않는다. float 초로 매번 더해나가면 오래 돌릴수록 어긋난다

주파수는 하드웨어마다 다를 수 있으므로 상수로 박으면 안 된다.
(요즘 Windows는 대개 10,000,000 → 1틱 = 100ns)

**두 함수는 시그니처가 `BOOL f(LARGE_INTEGER*)` 로 완전히 같아서 바꿔 써도 컴파일러가 못 잡는다.**

> **직접 확인**: `Tick()`에서 실수로 `Frequency`를 부르자 첫 프레임에 거대한 음수가 나오고,
> `m_lastTime`이 주파수 값으로 덮어써져 **이후 계속 `0.000000`** 이 나왔다.
> 클램프가 위쪽만 자르고 있어서(`if (dt > kMax)`) 음수는 그대로 통과했다.

`GetTickCount64`(약 10~16ms)나 `timeGetTime`(1ms)은 **눈금이 한 프레임(16.6ms)과 비슷해서**
프레임 측정에 쓸 수 없다. 측정 대상보다 눈금이 굵으면 의미가 없다.

## C++

### Q. 지역 변수의 `const` / `constexpr` / `static`은 각각 뭐가 다른가

- **`static`** = 저장 기간이 정적. 함수를 벗어나도 살아있고 **초기화는 한 번뿐**
- **`constexpr`** = 값이 **컴파일 타임에 확정**. 자동으로 `const`

| 형태 | 저장 기간 | 매 호출 초기화? |
|---|---|---|
| `const T x = ...` | 자동(스택) | 이론상 매번 |
| `static const T x = ...` | 정적 | 최초 1회 |
| `static constexpr T x = ...` | 정적 | **코드 자체가 생성되지 않음** |

주의: 지역 static이 **동적 초기화**되는 경우(`static std::string s = Load();`)에는
스레드 안전한 1회 초기화를 위해 **가드 변수 검사**가 매 호출 삽입된다. 항상 공짜는 아니다.

### Q. `#pragma comment(lib, ...)`는 헤더와 cpp 중 어디에

**cpp.** 링크 대상은 구현 세부사항이므로, 그 헤더를 include하는 모든 파일에 전파될 이유가 없다.
헤더는 "무엇을 할 수 있는가", cpp는 "어떻게 하는가"를 담는다.

### Q. `ComPtr`은 무엇을 해주나

D3D 객체는 COM 객체라 내부 참조 카운트를 가지며, 원래는 `Release()`를 직접 불러야 한다.
`ComPtr`은 이를 자동화하는 스마트 포인터(RAII)다.
누락하면 GPU 리소스가 새고, 디버그 레이어가 종료 시 "살아있는 객체 N개"를 보고한다.

### Q. `T x = {};` 는 왜 0 초기화가 아닌가

**집합체(aggregate) 초기화** 규칙 때문이다. 멤버에 기본값(NSDMI)이 선언돼 있으면 0이 아니라 **그 값**이 들어간다.

```cpp
struct SpriteDesc
{
    float x = 0.0f;
    DirectX::XMFLOAT2 origin{ 0.5f, 0.5f };   // NSDMI
};

SpriteDesc d = {};   // origin은 (0,0)이 아니라 (0.5, 0.5)
```

빈 `{}`로 초기화하면 명시되지 않은 멤버는 **NSDMI가 있으면 그 값**, 없으면 값 초기화(0)를 받는다.
C++11에서는 NSDMI가 있으면 집합체가 아니었으나 C++14부터 허용됐다. 이 프로젝트는 `/std:c++17`.

함정은 **`D3D11_BUFFER_DESC bd = {};` 처럼 실제로 "전부 0"을 의도하는 관용구와 생김새가 같다**는 점이다.
한 파일 안에서 두 의미로 쓰이면 읽는 쪽이 오해한다. 기본값을 쓸 거면 `SpriteDesc d;` 가 의도가 명확하다.

### Q. 지역 변수의 주소를 함수 밖으로 내보내면 왜 안 되나

지역 변수는 그 함수의 **스택 프레임**에 있고, 함수가 반환되면 그 영역은 회수된다.
다음 함수 호출이 곧바로 같은 자리를 덮어쓴다.

```cpp
wchar_t* GetInfo()
{
    wchar_t buf[256];
    swprintf_s(buf, L"...");
    return buf;          // 곧 사라질 메모리의 주소
}
```

호출부가 이 포인터를 쓰는 시점에는 이미 다른 값이 들어 있다.
**에러가 아니라 쓰레기 값이 나온다**는 게 이 버그의 특징이다.

같은 문제가 여러 모습으로 나타난다. 하루에 세 번 겪었다.

| 형태 | 사라지는 것 | 증상 |
|---|---|---|
| `return buf;` (지역 배열) | 스택 배열 | 문자열이 깨져 나옴 |
| `AnimationClip walk; SetClip(&walk);` | 지역 구조체 + 내부 vector의 힙 버퍼 | 애니메이션이 안 나오거나 크래시 |
| `Texture tex = m_texture; Draw(tex, …)` | 루프 지역 변수 | 텍스처 전환이 감지 안 됨 + 댕글링 |

전부 **"주소를 보관하는 쪽이 대상보다 오래 산다"** 는 하나의 문제다.
참조나 포인터를 저장하려면 **대상의 수명이 보관자보다 길어야** 한다.

#### 왜 세 번이나 반복했나

C#과 JavaScript를 오래 쓰다 보니 **객체 수명을 의식하지 않는 감각이 굳어 있었다.**
GC가 있는 언어에서는 참조를 넘겨도 대상이 살아 있는 것이 보장되지만, C++은 그렇지 않다.

아는 내용이었는데도 형태만 바꿔 반복한 것은 **지식이 없어서가 아니라 그 지식을 꺼내 쓰는
습관이 사라졌기 때문**이다. 이후로는 참조를 저장하는 코드를 볼 때 "이 대상은 누가 소유하고
얼마나 사는가"를 먼저 확인하게 됐다.

다만 습관은 다시 무뎌질 수 있으므로, **컴파일러가 대신 잡게 하는 편이 확실하다.**
아래 "리소스를 소유한 클래스는 왜 복사를 막아야 하나" 항목이 그 처방이다.

해결책은 셋 중 하나다.

- **소유자를 오래 사는 곳에 두고** 포인터로 가리킨다 — `m_walkClip`을 `App` 멤버로
- **값을 복사해 소유한다** — `std::wstring` 반환 (내용을 자기 힙 버퍼에 복사)
- **호출자가 버퍼를 넘긴다** — `void GetInfo(wchar_t* out, size_t count)`

MSVC는 `C4172: returning address of local variable or temporary` 로 경고한다.
이 계열은 컴파일러가 거의 항상 잡아주므로 **경고를 흘려보내지 말 것.**

### Q. 리소스를 소유한 클래스는 왜 복사를 막아야 하나

`Texture`, `Shader`, `SpriteBatch` 처럼 GPU 리소스를 쥔 클래스는 복사되면 안 된다.
그런데 멤버가 전부 복사 가능하면(`ComPtr`, `std::vector`) **컴파일러가 복사 생성자와
대입 연산자를 자동으로 만들어준다.** 그래서 실수로 복사해도 조용히 컴파일된다.

```cpp
class SpriteBatch
{
public:
    SpriteBatch() = default;                              // ← 반드시 같이
    SpriteBatch(const SpriteBatch&) = delete;
    SpriteBatch& operator=(const SpriteBatch&) = delete;
```

**`= default` 를 빠뜨리면 안 된다.** 생성자를 하나라도 직접 선언하면 기본 생성자가
자동 생성되지 않아서, 멤버로 선언하는 곳에서 `C2512`(적절한 기본 생성자가 없음)가 난다.
`delete` 로 지웠는데 "없다"는 에러가 나서 헷갈리는 자리다.

**아래쪽만 막아도 위로 전파된다.** 멤버 중 하나라도 복사 불가면 그걸 품은 클래스의
복사도 자동으로 삭제된다. `SpriteBatch`가 `Shader`를 값으로 들고 있으므로,
`Shader`만 막아도 `SpriteBatch`는 따라서 막힌다. **밑바닥 한 곳을 잠그면 위가 전부 잠긴다.**

부수 효과: 복사 생성자를 선언하면 **이동(move) 생성자도 자동 생성이 막힌다.**
컨테이너에 담거나 반환할 일이 생기면 `= default` 로 따로 열어야 한다.

> 이 두 줄이 있었다면 오늘 두 개의 버그가 **컴파일 에러로** 잡혔다 —
> `Texture tex; tex = m_texture;` 와 `m_batch = m_naiveBatch;`.
> 타입 시스템으로 실수를 막는 쪽이 리뷰로 잡는 것보다 확실하다.

### Q. 참조 멤버는 왜 다른 대상을 가리킬 수 없나

참조는 **초기화 시점에 대상이 정해지고 이후 바꿀 수 없다.** 포인터와의 결정적 차이다.

```cpp
SpriteBatch& m_batch = m_spriteBatch;

m_batch = m_naiveBatch;   // 재바인딩이 아니라 복사 대입!
```

`m_batch = X` 는 "m_batch가 X를 가리키게 하라"가 아니라 **`m_spriteBatch = X`** 다.
원래 객체의 내용이 통째로 덮어써지고 되돌릴 수도 없다.
용량 4096짜리 배치가 용량 1짜리로 영구히 바뀌어, 토글을 되돌려도 복구되지 않았다.

**가리키는 대상이 바뀌어야 한다면 포인터**를 써야 한다.

```cpp
SpriteBatch* m_batch = nullptr;
m_batch = useBatching ? &m_spriteBatch : &m_naiveBatch;
```

포인터를 쓰면 **같은 사실을 두 곳(플래그와 포인터)에 들고 있게** 되므로,
바꾸는 지점을 한 곳으로 모으는 게 안전하다.

```cpp
void App::ChangeBatchState(bool useBatching)
{
    m_useBatching = useBatching;
    m_batch = useBatching ? &m_spriteBatch : &m_naiveBatch;   // 항상 함께
}
```

매번 계산하는 함수(`GetBatch()`)로 두면 동기화할 상태 자체가 없어지지만,
호출부가 늘어난다. 바뀌는 빈도가 낮으면 포인터 + 단일 갱신 지점이 낫다.

## Direct3D 11

### Q. `ID3DBlob`이란

**크기 정보를 가진 이진 데이터 덩어리**(Binary Large OBject). 메서드는 사실상 두 개뿐이다.

```cpp
void*  GetBufferPointer();
SIZE_T GetBufferSize();
```

크기를 미리 알 수 없는 데이터를 API가 할당해 통째로 넘겨주기 위한 장치다.
같은 Blob이 **컴파일된 셰이더 바이트코드**를 담기도 하고 **에러 메시지 문자열**을 담기도 한다.
내용의 타입 정보는 없으므로, 문자열로 쓰려면 `static_cast<const char*>`로 해석해줘야 한다.

### Q. Device / DeviceContext / SwapChain의 역할 차이

| 객체 | 역할 |
|---|---|
| `Device` | 리소스 **생성** |
| `DeviceContext` | 렌더 **명령 발행** |
| `SwapChain` | 화면 버퍼 관리, `Present` |

분리된 이유는 멀티스레딩이다. `Device`는 스레드 안전하지만 `DeviceContext`는 아니다.

### Q. 백버퍼와 `RenderTargetView`는 왜 따로인가

백버퍼 자체는 그냥 `ID3D11Texture2D`(메모리)다.
**"이 텍스처를 어떤 용도로 쓸 것인가"** 를 선언하는 게 View다.
같은 텍스처를 렌더타겟으로도, 셰이더 입력(SRV)으로도 쓸 수 있고 그때마다 다른 View를 붙인다.

### Q. `CreateInputLayout`이 셰이더 바이트코드를 요구하는 이유

**선언한 정점 구조와 셰이더의 실제 입력 시그니처가 맞는지 생성 시점에 검증**하기 위해서다.
시맨틱 이름이나 개수가 어긋나면 여기서 실패하므로, 런타임에 화면이 깨지는 대신
초기화 단계에서 문제를 잡는다.

### Q. `SV_POSITION`은 왜 `float4`여야 하나

래스터라이저가 **동차 좌표(homogeneous coordinates)** 를 기대하기 때문이다.
`w` 성분으로 원근 나눗셈을 수행하는 구조라 2D든 3D든 4성분이 필요하다.
2D에서는 `float4(pos, 1.0f)`로 `w`에 1을 넣는데, "나누지 마라(1로 나눠라)"는 뜻이다.

### Q. `D3D11_SAMPLER_DESC`의 각 필드

**`Filter`** — 텍셀과 화면 픽셀이 1:1이 아닐 때 색을 정하는 방식.
이름은 `MIN`(축소) / `MAG`(확대) / `MIP`(밉 레벨 전환) 세 구간으로 나뉘며,
각각 `POINT`(최근접, 선명·계단) 또는 `LINEAR`(4텍셀 보간, 부드러움·흐림)를 고른다.

**`AddressU/V/W`** — UV가 0~1을 벗어날 때. `WRAP`(반복) / `CLAMP`(가장자리 고정) /
`MIRROR` / `BORDER`. U=가로, V=세로, W=깊이(3D용).

**나머지** — `ComparisonFunc`(그림자 맵 비교 샘플러용), `MinLOD`/`MaxLOD`(밉 범위 제한),
`MipLODBias`(밉 선택 보정), `MaxAnisotropy`(`ANISOTROPIC` 필터 전용),
`BorderColor`(`BORDER` 모드 전용).

이 프로젝트는 밉맵을 만들지 않으므로(`MipLevels = 1`) 밉 관련 필드는 영향이 없다.

### Q. 텍스처와 샘플러를 왜 분리하나

텍스처는 *무엇을 읽는가*, 샘플러는 *어떻게 읽는가*다.
같은 텍스처를 선명하게도 부드럽게도 읽을 수 있어야 하고, 반대로 여러 텍스처가 같은 읽기 방식을
공유하는 게 보통이다. 그래서 샘플러는 몇 개만 만들어 재사용한다.

### Q. `D3D11_BLEND_DESC`의 각 필드

계산식은 다음과 같다.

```
RGB   : 결과.rgb = (Src.rgb × SrcBlend)      [BlendOp]      (Dest.rgb × DestBlend)
Alpha : 결과.a   = (Src.a   × SrcBlendAlpha) [BlendOpAlpha] (Dest.a   × DestBlendAlpha)
```

`Src`는 지금 그리는 픽셀, `Dest`는 이미 화면에 있던 픽셀이다.
`BlendOp`에는 `ADD` / `SUBTRACT` / `REV_SUBTRACT` / `MIN` / `MAX`가 들어간다.
`RenderTargetWriteMask`는 R/G/B/A 중 어느 채널에 쓸지 제어한다.

RGB와 알파를 따로 두는 이유는, 오프스크린 렌더타겟에 그린 뒤 나중에 합성할 때
알파값이 정확해야 하기 때문이다. 백버퍼에 직접 그릴 때는 알파가 무시된다.

**자주 쓰는 조합**

| 용도 | SrcBlend | DestBlend |
|---|---|---|
| 알파 블렌딩 | `SRC_ALPHA` | `INV_SRC_ALPHA` |
| 가산(빛·이펙트) | `SRC_ALPHA` | `ONE` |
| 곱셈(그림자) | `DEST_COLOR` | `ZERO` |
| 프리멀티플라이드 | `ONE` | `INV_SRC_ALPHA` |

### Q. 왜 `RenderTarget[0]`만 채우나

`D3D11_BLEND_DESC::IndependentBlendEnable`이 `FALSE`(기본)이면
D3D가 **`RenderTarget[0]`의 설정을 모든 렌더타겟에 적용**하고 `[1]`~`[7]`은 읽지 않는다.
`TRUE`로 두면 렌더타겟마다 다른 블렌딩을 줄 수 있다.

### Q. 다중 렌더타겟(MRT)은 언제 쓰나

한 번의 드로우로 여러 정보를 동시에 기록할 때다. 픽셀 셰이더가 `SV_Target0`, `SV_Target1`…로
여러 값을 내보낸다.

- **디퍼드 렌더링** — 색·법선·깊이를 G-buffer에 한꺼번에 기록
- **포스트 프로세싱** — 화면과 함께 "밝은 부분"을 따로 뽑아 블룸에 사용

2D 스프라이트 렌더러에서는 거의 쓰지 않는다.

### Q. 인덱스 버퍼는 왜 쓰나

쿼드는 삼각형 2개라 정점이 6개 필요하지만 실제로 서로 다른 정점은 4개다.
인덱스는 "이 정점을 다시 써라"는 번호표다.

배칭에서 진가가 드러난다. **정점은 매 프레임 바뀌지만(동적), 인덱스 패턴
`0,1,2,0,2,3`은 영원히 고정(정적)** 이므로, 인덱스 버퍼는 최대 개수만큼 미리 만들어두고
다시 건드리지 않는다. 이 분리가 배칭 성능의 기반이 된다.

### Q. `SysMemPitch`란

이미지 **한 줄의 바이트 수**(`너비 × 채널당 바이트`).
GPU가 데이터를 줄 단위로 읽으므로 필요하며, 틀리면 이미지가 대각선으로 밀려 나타난다.

### Q. 와인딩 순서

D3D11 기본값은 **시계 방향 = 앞면**이고, 뒷면은 그리지 않고 버린다(백페이스 컬링).
정점 순서를 반대로 넣으면 **에러 없이 조용히 아무것도 안 보인다.**
화면에 아무것도 안 나올 때 첫 번째로 의심할 곳.

### Q. 2D에서 백페이스 컬링은 의미가 있나

없다. `CULL_NONE`이 정답이다.

3D에서 컬링이 이득인 이유는 닫힌 메시의 **절반이 항상 반대편을 향해 어차피 안 보이기** 때문이다.
그 절반을 래스터화 전에 버려 픽셀 처리를 아낀다.

2D 스프라이트는 전부 카메라를 정면으로 보는 평면이라 **버릴 뒷면이 존재하지 않는다.**
뒷면 판정이 나오는 건 음수 스케일(좌우 반전)로 와인딩이 뒤집혔을 때뿐이고, 그건 보고 싶었던 것이다.
즉 컬링을 켜서 버려지는 건 **0개이거나, 보고 싶었던 것** 둘 중 하나다.

> **직접 확인**: `w`를 음수로 바꾸면 `CULL_BACK`에서 스프라이트가 전부 사라지고,
> `CULL_NONE`과 `CULL_FRONT`에서는 정상적으로 나온다.

반전되는 객체만 `CULL_NONE`, 나머지는 `CULL_BACK`으로 나누는 것도 손해다.
`RSSetState`는 파이프라인 상태 변경이라 **텍스처 교체와 똑같이 배치를 끊는다.**
존재하지 않는 이득을 얻으려고 실제 드로우콜만 늘리는 셈이다.

XNA/MonoGame `SpriteBatch`, Unity 2D, Godot 2D가 모두 컬링을 끈다.
단, 빌보드나 2.5D처럼 3D 요소를 섞으면 이야기가 달라진다.

### Q. 상태 객체는 왜 수정할 수 없나

블렌드·래스터라이저·샘플러·뎁스스텐실 상태 객체는 전부 **불변**이다.
`GetDesc()`로 설정을 꺼내 고쳐도 원본에는 반영되지 않는다 — 꺼내온 것은 **CPU 쪽 구조체 복사본**일 뿐이다.

```cpp
// 아무 효과 없음. 여전히 원래 상태가 바인딩된다
m_blendState->GetDesc(&bd);
bd.RenderTarget[0].DestBlend = D3D11_BLEND_ONE;
ctx->OMSetBlendState(m_blendState.Get(), factor, 0xFFFFFFFF);
```

`CreateBlendState()` 시점에 드라이버가 설정을 **검증하고 하드웨어 레지스터 값으로 미리 번역**해두기 때문이다.
그 비용을 로딩 때 한 번만 치르려는 설계이므로, 나중에 바꿀 수 있게 하면 의미가 없어진다.

D3D9는 `SetRenderState(D3DRS_DESTBLEND, ...)`처럼 개별 설정을 호출할 때마다 바꿨고,
D3D10에서 상태 객체 모델로 바뀐 이유가 바로 이 비용이다.

따라서 **필요한 조합을 초기화 때 전부 만들어두고 교체**하는 것이 유일한 방법이다.
불변인 것은 만들어진 **상태 객체**이지 `_DESC` 구조체가 아니므로, desc는 고쳐서 재사용해도 된다.

```cpp
bsd.RenderTarget[0].DestBlend = D3D11_BLEND_INV_SRC_ALPHA;
device->CreateBlendState(&bsd, &m_blendAlpha);

bsd.RenderTarget[0].DestBlend = D3D11_BLEND_ONE;   // desc는 얼마든지 수정 가능
device->CreateBlendState(&bsd, &m_blendAdditive);
```

이 버그는 **코드는 그럴듯한데 조용히 아무 일도 안 하는** 종류다.
같은 계열로 "샘플러를 만들어놓고 `PSSetSamplers`를 안 불러 기본 샘플러가 쓰인" 경우가 있었다.

## 설계

### Q. 무엇이 배치를 끊는가

**파이프라인 상태는 끊고, 정점 데이터는 끊지 않는다.**

| 스프라이트마다 다른 것 | 이 프로젝트의 처리 | 상태로 처리했다면 |
|---|---|---|
| 위치·회전·크기 | CPU에서 정점 좌표 계산 | 상수 버퍼 변경 → 끊김 |
| 색상(틴트) | 정점 색상 | 상수 버퍼 변경 → 끊김 |
| 그림 종류 | UV (아틀라스) | 텍스처 변경 → 끊김 |
| 좌우 반전 | 음수 크기 + `CULL_NONE` | 컬 모드 변경 → 끊김 |
| 블렌드 방식 | **배치 단위로 지정** | 스프라이트별 지정 → 끊김 |

원칙 하나가 스프라이트 배처의 설계를 전부 결정한다.
회전을 상수 버퍼 대신 CPU에서 계산하는 이유, 틴트를 정점 색상에 넣는 이유,
아틀라스를 쓰는 이유, 컬 모드를 통일하는 이유가 모두 같다.

블렌드처럼 정점에 넣을 수 없는 것은 **API가 제약을 드러내게** 한다.
`Begin(camera, blendMode)`로 받으면 "배치 중간에는 못 바꾼다"가 시그니처에 나타난다.
XNA `SpriteBatch.Begin(sortMode, blendState)`도 같은 형태다.

> **직접 확인**: 같은 텍스처 12장을 알파 10 + 가산 2로 나누면 드로우콜 2회.
> 텍스처 전환 0, 버퍼 포화 0이므로 끊긴 원인이 블렌드 모드임이 수치로 드러난다.

### Q. 카운터는 어디서 초기화해야 하나

"무엇을 재는가"가 아니라 **"어느 구간을 재는가"** 로 결정한다.

드로우콜 카운터를 `Begin()`에서 초기화하면 집계 구간이 **배치**가 된다.
한 프레임에 `Begin`/`End`가 여러 번 오면 마지막 배치 숫자만 남아 프레임 전체를 알 수 없다.

`SpriteBatch`에는 **프레임이라는 개념이 없다.** `Begin`/`End` 쌍만 알 뿐,
그게 프레임에 몇 번 오는지는 호출자가 정한다. 그래서 집계 구간도 호출자가 정하도록
`ResetStats()`를 공개하고 `Begin`에서는 카운터를 건드리지 않는다.

같은 기준으로 `m_cpuVertices.clear()`와 `m_currentTexture = nullptr`는 `Begin`에 남는다.
그건 통계가 아니라 **배치 상태**이고, 수명이 실제로 배치이기 때문이다.

### Q. 플러시 원인별 집계를 호출부에서 세면 왜 안 되나

`Flush()`는 정점이 비어 있으면 early-return한다. 즉 **불러도 드로우콜이 안 나가는 경우**가 있다.

```
버퍼 포화로 Flush → 정점 0개, m_currentTexture는 남아 있음
    → 다음 Draw에서 텍스처가 바뀌면 텍스처 분기가 걸림
    → Flush는 early-return (그리지 않음)
    → 호출부에서 셌다면 카운터만 올라감
```

집계는 **early-return 가드를 통과한 뒤**, 실제로 `DrawIndexed`가 나간 자리에서 해야 한다.
그래서 이유를 `Flush(FlushReason)` 인자로 넘기는 구조를 택했다.

검산식: `drawCallCount == textureSwitchCount + overflowCount + endOfBatchCount`.
배치가 몇 개든 항상 성립하며, 깨지면 어딘가 새고 있는 것이다.

### Q. BOM — 왜 C++과 HLSL의 요구가 정반대인가

| 컴파일러 | BOM |
|---|---|

### Q. 화면이 이상할 때 무엇부터 보나

1. **VS 출력 창(디버그)** — 디버그 레이어(`D3D11_CREATE_DEVICE_DEBUG`)가 잘못된 바인딩,
   크기 불일치, 해제되지 않은 객체를 알려준다
2. **그래픽 디버거** (`디버그 > 그래픽 > 그래픽 디버깅 시작`) — 프레임을 캡처해
   파이프라인 각 단계에 실제로 무엇이 들어갔는지 확인한다

추측으로 코드를 고치기 전에 **먼저 볼 것.**

### Q. 셰이더를 런타임에 컴파일하는 이유

셰이더만 고치고 다시 실행하면 되므로 반복 속도가 빠르고, 컴파일 오류를 실행 중에 확인할 수 있다.
대신 **에러 블롭 출력이 필수**다. 없으면 실패 사실만 알고 원인을 모른다.

배포 시점에는 미리 `.cso`로 컴파일해 두는 방식이 시작 시간과 컴파일러 의존성 면에서 유리하다.
